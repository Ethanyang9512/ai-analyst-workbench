# 质量关

这一篇讲一份成品发出去之前要过哪几道关、每道关查什么和查不了什么、验收怎么分档，以及护栏挡什么。

**结论：** 四层关卡由便宜到贵：程序检查（几秒）→ 两位验收员（几分钟）→ 对抗式审查（重要交付）→ 用户。每层只查自己擅长的；程序通过不等于没问题，验收员说“能发”也不等于用户会满意，所以每层都不能替代下一层。

## 四层关卡

| 层 | 谁来查 | 查什么 | 查不了什么 |
|---|---|---|---|
| 程序检查 | Python 脚本 | 禁用词、文字重叠和出界、内部痕迹、页码引用、同一个东西几种写法、数据包没重跑 | 意思对不对、图表达没表达结论、颜色难不难分 |
| 子代理验收 | 读者验收员、图表数字验收员 | 没背景的人看不看得懂；图上的毛病；数字和数据源对不对 | 业务判断本身对不对；用户的个人口味 |
| 对抗式审查 | 分析助手换位进攻，复杂对象叫子代理并行 | 假设、口径、边界条件、业务合理性、使用者视角 | 用户没说出口的标准 |
| 用户 | 分析师本人 | 最终判断、手改定稿 | — |

## 程序检查

| 程序 | 查什么 | 退出码 |
|---|---|---|
| `skills/ethan-report-writing/scripts/style_lint.py` | 禁用词台账里的硬禁词（台账追加即生效）；% 和 pt 混用、第二人称等给警告 | 1＝有硬禁命中，0＝没有（警告不拦） |
| `skills/ethan-report-writing/scripts/figcheck.py` | 两段文字互相重叠、折线穿过文字、文字出界或被裁掉 | 有问题打印出来，并在图旁写一份 `.check.json` |
| `skills/ethan-report-writing/scripts/trace_scan.py` | 给业务看的稿子里不该出现的东西：协作方名字、过程用词（数据包、需求包、审核报告……）、本机路径、内部轮次号 | 1＝有命中，0＝只有待判断或没有 |
| `skills/ethan-report-writing/scripts/deckcheck.py` | 幻灯片三个子命令：`text` 查禁用词、对象编号、同一个东西几种写法、不存在的“第 N 页”；`pdf` 查词被拆在两行、文字压出页面；`scope` 算出这次改了哪几页、哪些页受影响、建议档位 | 0＝没有必须改，1＝有必须改，2＝没查成（不能当通过） |
| `skills/ethan-slide-deck/scripts/check_deck.py` | PPT 七项：文件完整性、非法色值、元素越界、文字块重叠、术语黑名单、文字溢出、图表数据标签位置 | 1＝有问题 |
| `skills/ethan-data-package-review/scripts/pkgcheck.py` | 数据包：和上一轮比文件指纹、行数；说改了却没重跑；Excel 公式缓存为空；明文个人信息；日期列缺天 | 3＝有“说改了没重跑”，1＝有别的新的严重问题，0＝没有 |

用法上的三条规矩：

- 程序报的“必须改”先改掉，再交给验收员。
- 程序报错、没查成、或者那一项它本来就不查，都不能写成“通过”。
- `deckcheck.py` 会读项目约定页 `_CONVENTIONS.md` 末尾的 json 检查块（不用的词、统一写法、对象名和编号的对应等），所以同一类纠正进了约定页，下次就由程序拦。

## 分档验收

为什么分档：验收员是改稿一轮里很费时间的一环，而改一个错字和重写整篇如果走同一套流程，小改就会被拖慢，大家也会开始跳过验收。所以按改动大小分三档：

| 档 | 什么时候 | 两位验收员看什么 |
|---|---|---|
| 小改 small | 不超过 3 页，没改数字、页标题、页数、页序和图 | 只看改动页；图表数字验收员只查版面和约定页里“页面上不出现的” |
| 大改 page | 其余情况 | 改动页和受影响的页 |
| 全稿 full | 新写的第一版；用户说定稿、要汇报、发给别人或全面检查；`accept_record.py status` 建议通读 | 通读全稿 |

- 档位以 `deckcheck.py scope` 的结论和 `accept_record.py status` 的建议为准；用户说定稿或要汇报时只往高档升。
- `status` 的建议：从最近一次全稿验收算起，满 5 条记录、或累计涉及 8 页、或超过 3 天，就建议下一次改稿后通读一次——防止一路小改积累出一份没人通读过的稿子。
- 没有 `scope` 可用时（文档、Excel）：新写按全稿；只改字词、标点或不超过 3 处数字按小改；其余按大改，并在记录里写明理由。
- **只有“必须改”才返工。** 建议最多 3 条，记进验收底稿；会改变用户判断的才在回复里提一句。

## 两位验收员

验收员是两个只读的子代理，定义在 [agents/](../agents/)。它们不改文件、不发消息、不替作者改稿。

| | 读者验收员 `cold-reader` | 图表数字验收员 `chart-number-checker` |
|---|---|---|
| 身份 | 没有项目背景的业务同事（运营、产品或管理岗），第一次看这份材料 | 严格的图表与数字验收员 |
| 读什么 | 只读成品，以及调用方给的术语表和骨架；**不读**项目里的其他文件 | 成品、逐页图片、数据源、项目约定页 |
| 交回什么 | 三句话复述、看不懂的词、逻辑跳跃、每张图读出了什么、内部痕迹 | 逐张图的毛病（十项清单）、至少抽核 8 个数、对照约定页和五条讲法 |
| 结论 | 必须改全部列出；应该改最多 3 条 | 同左；文字重叠、被压住、被截断一律算必须改 |

**为什么用另一个子代理，而不是让分析助手自查：** 写的一方带着全部背景，读自己的稿子会自动脑补；读者验收员看不到项目文件，读不懂就是真读不懂。图表数字验收员要回到数据源用代码复算，而不是看着“差不多”。

图表数字验收员每次都对照的**五条讲法**（出自 `ethan-pyramid-storyline` 的「指标波动的讲法」）：

1. 瀑布图的起点和终点，就是标题里那个指标的两个值，中间各柱加起来等于变化量。
2. 解释比率的变化时，把分母的变化也算进去（先看构成变没变），不只拆分子。
3. 放在一起比的两组数口径一致：同一套标签、同一个来源、同一时间范围。
4. 标题的结论，在本页的图里第一眼看得出来。
5. 本页最显眼的数或词，不会引出和主线无关的追问。

前三条违反算必须改，后两条算建议。

## 验收记录和验收门

- **写记录**：必须改的修完后运行
  ```bash
  python3 $AAW_RUNTIME/tools/accept_record.py write --file <文件> \
    --tier small|page|full --pages "<页>" --reader "<读者验收结果>" --visual "<图表数字验收结果>"
  ```
  记录写在工作区最上层的 `_acceptance/records.jsonl`，按文件内容的指纹（SHA-256）记。文件内容一变，就要重新验收、重新记录。
- **验收门**：钩子 `gate.py` 在 PPT、Excel、Word、PDF 发到飞书（或导入成飞书文档、新建飞书文档）之前，查这份文件有没有记录。
- **两种模式**：提醒模式（默认），没有记录只在结果旁加一段提醒；强制模式（钩子状态目录下有 `GATE_ENFORCE` 文件），没有记录就拦下并说明怎么做。
- **为什么要分三条命令**：钩子在命令执行之前运行，同一条命令里才生成的文件和记录这时还不存在。所以“生成文件、写记录、发送”分开写。
- **门要能找到文件**：它按命令里写明的 `cd`、变量赋值和 `for` 清单推算文件位置；路径里有未知变量、通配符或命令替换时推算不出，按“没有记录”处理。发送命令里直接写出文件名最稳。
- **留痕放行**：用户明确说不用验收、或者发的是中间文件时，在发送命令前加 `ACCEPT_SKIP='理由'`，会记一笔。

## 对抗式审查

技能 [ethan-critical-review](../skills/ethan-critical-review/) 是重要交付物的默认质量关，不必等用户开口。

- **第一性原理**：把成品拆回最底层的事实和假设，逐条问“这是数据支持的，还是想当然的？来源是什么？”。“上一版就是这样”“业内惯例”都不算来源。
- **对抗式**：换位成一个想把它驳倒的人，从 3 到 5 个互相独立的视角进攻：逻辑一致性、数据口径（时间对齐、单位、去重）、边界条件、业务合理性、使用者视角。
- **产出**：每条发现标 P1 / P2 / P3，写清“在什么输入下会出什么错”；修一条验一条，不修完就宣布通过。
- **零发现也要汇报攻了哪些视角**。“没问题”三个字不算审查报告。
- **质量关不是扩大范围的理由**：审查发现的范围外问题列给用户，不顺手改。
- **一个提醒**：对抗式审查容易让作者往稿子里加“防杠句”（预先替人反驳质疑的句子），而这正是用户最常删掉的一类。读者真会问的，放进“需要关注”；作者怕被质疑才写的，删掉。

## 护栏

钩子 `guard.py` 在每条 Bash 命令执行前运行，拦下面五类，其余一律放行：

| 拦什么 | 防什么 |
|---|---|
| 启停或杀掉桥进程 | 用错命令把桥悄悄换掉或停掉，用户在飞书里找不到助手 |
| 发飞书消息时没带 `--as bot` | 以用户身份发出的消息会被桥当成新消息，助手又回复自己，循环下去（回环） |
| 改自己的护栏、规则和设置（runtime 目录、各处 `.claude/settings*.json`、`~/.claude/CLAUDE.md`、`~/.claude/agents/`） | 材料里夹带的指令诱导分析助手放宽自己的规矩 |
| 调用密钥工具、读钥匙串或密钥文件 | 泄露令牌和凭据 |
| 发到本轮所在群以外的群或个人 | 发错群，把一个项目的内容泄到另一个群。用户在本群明确要求时，命令前加 `ALLOW_OTHER_TARGET='用户原话'` 放行并记日志 |

取舍：

- **只认明显的写法，挡不住刻意绕过。** 它是防误操作和防材料里夹带指令的门槛，不是安全边界。
- **解析出异常一律放行。** 宁可漏拦一条，也不能因为钩子自己的毛病拦住所有命令。
- **日志只记规则名和时间，不记命令原文**——数据包里可能有明文口令。
- **第二道门**：工作区设置里的 `permissions.deny` 禁止用改文件的工具改上面这些地方。在作者使用的 Claude Code 版本上实测，只写 `Edit(...)` 规则就能管住全部改文件的工具，在完全权限模式下也生效；换版本后请自己再验一次。

## 会前追问清单

用户说要汇报、汇报前或给领导看时，分析助手在回复末尾附一份《会前追问清单》：8 到 10 个领导最可能问的问题，每题一句话答案、对应第几页、依据哪个数；答不了的写“现有材料答不了，需要……”。它只给用户看，不放进正式稿，也不另发文件。

# 改稿：怎么按意见改，以及用户手改里常见的规律

> `report-writing` 的参考文件。按用户意见改稿、或拿“交付版 → 用户定稿”提炼改法时读。下面的例子都是虚构的。

## 一、按意见改稿的做法

用户的意见常常是一串编号清单，一条消息里十来条，图文混着发。

1. **逐条编号回执**：按用户的编号一条条回，写清“怎么改的、在哪能看到（第几章、哪张图）”，不要合成一段叙述。
2. **回执前逐条实测**：一条意见常常牵连正文、表格、图注和口径说明好几处。给每条写一个程序能判定的检查（某个词在不在、两处数字是否一致），全部通过再回执，不凭“我改了哪几块”的记忆。
3. **没做的要说**：不建议做或做不到的，写“未做 + 原因”，不静默跳过。
4. **写出连带后果**：删掉一个建议后，原来挂在它下面的那部分（比如一块预算、一批用户）去了哪里，要在文档里交代。
5. **先改判断，再改措辞**：用户说某句“说法不对”，多半是判断本身有问题（例：“执行不到位”其实是“条件还不具备”），只换个说法不算改好。
6. 整轮改完，用 `critical-review` 从读者视角过一遍，P1、P2 修完再交。

## 二、从手改里提炼改法的纪律

- **用户顺手换掉的词不等于禁语。** 判据：同一个词在用户没重写的句子里是否也被改了。只在重写句里变了，就不是禁语。
- **做带格式的比对**：纯文本比对抓不到只改了加粗、列表的编辑，按段落和标记切开再比。
- **只记一次的先当观察**：同类改法第二次出现，才写进项目约定页（见 `SKILL.md`「修正即沉淀」）。

## 三、用户手改里常见的八条规律

下面是“交付版 → 定稿”对比里反复出现的改法。写第一版时就照着做，能省一轮返工。

1. **先讲已经发生的，再讲预测。** 例：把“过去三周的续费变化”挪到“下月预计”前面。读者先认下问题确实存在，才会听后面的推演。
2. **事实段不带论证尾巴。** 例：现状段末尾“……这说明必须调回原价”被整句删掉。论证放到建议那一章。
3. **缩写第一次出现写全称。** 例：“ARPU”第一次出现改成“每用户平均收入（ARPU）”。读者不一定都懂缩写。
4. **用业务开会时用的那个词。** 例：“扣不动的单”改成“扣款失败的订阅”。不自造简称，也不过分口语。
5. **数字要能口头复述。** 例：“3.0 倍”改成“3 倍”；“6,312 个，为周均的 128%”改成“约 6,300 个”。同一列小数位一致；绝对量后面补一个相对量（“多了约 1,200 个未续费，占当周到期的 6%”）。源数据和底稿保留原精度。
6. **一句一个意思。** 一句里出现第二个分号就该断开，例：“W5 发通知；W6 涨价；W7 起优惠订阅到期”拆成三句，各配一个数。
7. **汇报版只留一个口径。** 例：“三种预测方法下，下月续费率在 75.8%–78.6% 之间”改成“下月续费率预计约 77%”。几种算法怎么合看放详细版；风险照常写，但不在结论段反复自我削弱。
8. **少说“我们判断”，多说“数据显示”。** 例：“我们判断主要是涨价的影响”改成“数据显示，下降集中在涨了价的月付方案”。分析给的是测算结果，语气越平越像结论。

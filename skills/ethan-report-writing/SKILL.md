# 面向业务的报告写法

读这类文档的人要拿它去做决定、去转述，不会替作者补背景。所以这份技能管三件事：**写得让人一次读懂、数字经得起复核、同一个错误不出现第二次**。叙事骨架（先讲什么）归 `ethan-pyramid-storyline`，这里只管怎么写。

按需再读同目录的参考文件，不要一次全读：

| 什么时候 | 读哪个 |
|---|---|
| 要出图、做表、做 Excel 图表包 | `references/chart-style-guide.md` |
| 按用户意见改稿、拿用户手改稿提炼改法 | `references/revision-patterns.md` |
| 成品要写进飞书文档（插图、画板、覆盖重推） | `references/feishu-ops.md` |
| 记一条用户纠正、跑硬禁检查 | `references/style-lexicon.md`（台账，`scripts/style_lint.py` 直接读它） |

## 动笔前的三个问题

答不出来就先别写，写散的文档多半是跳过了这一步。

1. **读者是谁，读完要做什么决定或动作？**
2. **一句话结论是什么？** 写不出一句话，说明分析还没做完。
3. **哪个数最该被记住？** 它通常不是分析里算出来的第一个数。

第 3 问最容易答偏。例（虚构）：续费率报告开头写“整体续费率 77.0%”，读者真正想知道的是“这次下降有多少是人变了、多少是价格的影响”。能回答业务心里那个问题的数没算出来之前，不要急着写开头。

## 两种体裁

**说明类（方法论、模型说明）**分两部分：

1. 现状逻辑：一句话说清它是什么 → 规则表 → 计算步骤 → 一个带真实数字的例子 → 结果 → 待决定事项；
2. 使用说明：每张表干什么、哪些格子能改、改了会怎样、常见误区。

**分析报告**按“结论在前”排：

```
一、结论与建议      一句话结论 + 2–4 条要点；有待决定的事，用一张小表（事项 / 建议）
二、最重要的发现     单独成章，不埋在后面
三、读者必需的概念   只讲不懂就读不下去的部分
四…、分维度拆解与趋势
附：口径说明        放最后
```

- 分析时先拆解后结论，写的时候反过来。
- 口径细节后置，正文只留读者不知道就会误读的几条。
- 每个待决定事项都给建议，不写“需进一步讨论”。
- 章节标题和图标题分工：默认章节标题用中性的名词短语（对象 + 维度，例“到期订阅的构成变化”），结论放在章首句；图标题写读者一眼能在图上验证的结论。项目约定页另有规定时照项目。

## 语体

目标是规范的书面商务语体：句子完整，用测算、换算、校准、识别这类业务动词，保留读者熟悉的行业术语。两头都会被退回：

- 太学术：自造的框架名、模型术语。整段读一遍，业务看不懂就重写。
- 太口语：比喻、俚语、“说白了”一类引导语。

逐句去掉这几类：

| 去掉 | 例 | 改成 |
|---|---|---|
| 绝对化副词 | 完全不用维护 | 不需要维护 |
| 口语引导语 | 原因很简单： | 原因为： |
| 过程交代 | 经过三方会议确认后 | 直接给结论 |
| 第二人称 | 你在后台点导出 | 运营同事在后台点导出 |
| 自我评价 | 这是本版最有价值的一项 | 该机制的作用： |
| 挑数字的毛病 | 这个数有误导性 | 这个数包含了 X，因此另做了一次拆解 |

**口径按计算方式命名，不按覆盖范围命名。**“全站口径”会让人以为在和全站比；写“按到期日口径”“按扣款日口径”，比较时说“低于平均值”。

## 硬规则

- **% 和 pt 分清**：比率本身用 %（续费率 77.0%）；两个比率之差用 pt（比 W5 低 3.8pt）；相对变化用 %；金额、时长的差用原单位。单位由计算含义决定，不由“提升”“差距”这类词决定。
- 关键数字加粗；约数写“约”或“~”；数量单位（万、千、K）和小数位按项目约定页，没有约定时全文统一一种。
- 样本量、分母、区间合计保留总量和统计窗口；日均只能和它并列，不能替代分母。
- 要贴进飞书的文档：正文不用 LaTeX；复杂公式用公式块放在章节开头，简单的写成文字；不用代码块；表格用 Markdown 表格。
- 只给分析师看的技术细节可以另附，不进主交付。

## 修正即沉淀

用户的每一次纠正都是规则的来源。协议四条：

1. **当轮生效**：用户的原话纠正，当轮记下改法、出处和适用范围，不等用户说“记住”。先按本项目记（项目状态、本项目生成源）；同类纠正第二次出现，写进项目 `_CONVENTIONS.md`，能程序查的写进它的 json 块。用户说明适用于所有项目时才写进全局。
2. **推断要过门槛**：从用户改动里推断出的规则（不是原话），至少在 2 份文档里出现过才当规矩用，升进台账的「一、硬禁」表也一样。
3. **作废不删**：被新决定取代的条目挪到 `references/style-lexicon-archive.md`，写明作废日期和由哪条取代。
4. **冲突时**：用户原话 ＞ 项目约定页 ＞ 本技能 ＞ 智能体推断。

同一个词被纠正第二次，说明检查没跑或没拦住，要主动说明原因并补检查。整套写作规范设总字数上限（由用户定，按去掉空白后的字数量），当轮记纠正不受上限阻挡，超了等用户批准的“大扫除”再合并。

## 成对稿与考题

用户直接改了线上文档时，用发布时存的快照比出用户的改法，这是最有价值的风格样本。同时把这一对存下来，后面改技能时拿来考试：

```bash
python3 <本技能目录>/scripts/pairsnap.py save --project <项目> --doc <文档名> \
        --delivered <交付版快照> --final <用户改后的回读> [--root <存放目录>]
```

- 默认存到 `~/aaw-pairs`，可用 `--root`（写在 `save` 前后都行）或环境变量 `PAIRSNAP_ROOT` 改。存放处是助手日常不读的目录。
- 输出一行 JSON。`"heldout": true` 的这份留作考题：改法照常提取、照常记，但写到哪里（台账、约定页、术语表、项目状态、记忆、生成源）都标「考题来源：<id>」，考试时这些地方一起遮掉。成品里不能出现这个标记。
- 遮挡是出考卷的人做的事；日常干活照常用全部记忆和台账。
- 报错就照实说没存上，不要因此跳过提取改法。

## 让读者看懂

“看不懂”多半卡在术语、自造概念和“为什么这么算”，很少是嫌字多。所以：

- **术语表**：项目根目录放 `_glossary.md`，10 到 20 个词；一个概念全文一个叫法，第一次出现就地解释，不自造概念。
- **讲清为什么**：每个关键算法配一个带真实数字的例子，再加一句为什么这样算（为什么选这个分母、为什么这样加权）。
- **图优先**：解释逻辑、流程和口径差异时，先给图或对照表，再给一句结论。
- **改稿对照表**：按评论改稿时，交回“每条意见 → 属于哪类（答疑 / 局部改 / 全篇同类改 / 口径变化）→ 改了哪些位置”。

## 交付前自检

- [ ] 一句话结论写得出来，最该记住的数在第一屏。
- [ ] 单位对：比率差用 pt，相对变化用 %，金额时长用原单位；日均没有替代分母。
- [ ] 数字能加回去：分项加总等于合计，占比合计 100%，跨章节同一个数一致，“见第 X 章”的编号对。用脚本核，不靠目测。
- [ ] 每个公式后面有带数字的例子；图标题写结论；图和表没有同时上色抢注意力；口径细节已后置。
- [ ] `python3 <本技能目录>/scripts/style_lint.py <稿件>`：硬禁 0 命中，警告逐条判断。
- [ ] 出图：`python3 <本技能目录>/scripts/figcheck.py <出图脚本.py>`，或在脚本里用 `save_checked(fig, path)`。程序查不出颜色难分和“图不表达结论”，这两样还要自己看图。
- [ ] 给业务看的稿子：`python3 <本技能目录>/scripts/trace_scan.py <稿件> [--names 你的协作方名字]`，内部痕迹 0 命中。
- [ ] 幻灯片：`${AAW_PY:-python3} <本技能目录>/scripts/deckcheck.py scope|text|pdf …`（用法见同目录 `README.md`）。退出码 2 是“没查成”，不能当通过。
- [ ] 术语表里没有的专业词，换成表里的词，或第一次出现时解释并补进表。
- [ ] **自查只做减法**：交付前“按规范自查一遍”时，只改有规则依据或读者会看不懂的地方；读得懂的句子原样留着；数字不改，觉得不对先回源数据核，核不了就标出来问；改完不应比原稿长；回复里逐条列出改了哪里、依据哪条规则。
- [ ] 正式交付前过两位验收员：`cold-reader`（冷读）和 `chart-number-checker`（看图、核数）。必须改的修完后记一笔验收记录再发（用分析助手运行时时：`python3 "$AAW_RUNTIME/tools/accept_record.py" write …`；不用就跳过记录）。

最后自问：一个不懂建模的业务同事，能不能 10 分钟读懂并转述给别人？

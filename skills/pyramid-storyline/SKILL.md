# 答案先行的汇报骨架

一份材料读不下去，很少是因为句子不好，多半是因为顺序错了：作者按自己分析的顺序讲（先做了 A、再做了 B），读者却要先知道答案。本技能只管顺序和“每章那一句话”。

**最快的诊断**：只读各章的第一句。读出来的是完整结论，骨架就立住了；读出来的是“我们先看了……然后看了……”，就要重排。

## 动笔前先想清三件事

不必让用户再填一遍，用已经确认的背景在心里答完：

| 问题 | 决定什么 |
|---|---|
| 读者是谁？这次要回答什么、或者要他做什么？ | 解释的深度、证据的顺序 |
| 现有证据能支持到哪一步？ | 首句说多重：哪些是事实、哪些是判断、哪些还待验证 |
| 全篇最该被记住的那一两个数是什么？ | 放在第一章第一屏，其余数字进各章 |

不是每份材料都在请人拍板。讨论稿、盘点、数据还不全的时候，先把已知部分讲清楚，不为了套模板编一个结论。

## 决策类材料的默认骨架

```
第一层 答案   一、结论与建议：2–4 条结论（每条一句加粗判断 + 至多一句支撑）+ 一段建议
第二层 理由   二…N、一个问题一章：章首句就是这一章的结论，后面跟证据、原因、限制
第三层 依据   口径说明 / 附录：怎么算的、为什么这么算、数据从哪来
```

- **每章内部也倒过来**：首段给这一章的答案 → 证据（表或图，各配一句要点）→ 原因或限制 → 判定口径放章末。读者看到表之前已经知道结论，表只是验证。
- **开场压成两三句，不单独成章**：先说双方都认的事实，再说什么变了，然后是由此要回答的问题，紧接着给答案。这就是 SCQA（情境、冲突、问题、答案）的压缩版。

## 三种“一句话”的分工

| 位置 | 文档 | 汇报片 |
|---|---|---|
| 章节或页标题 | 中性的名词短语：对象 + 维度（“月付涨价前后的续费率对比”）；项目约定页另有规定时照项目 | 结论句：主语 + 方向 + 数字，可带“模块 \| ”前缀标明属于论证的哪一枝 |
| 章首句 | 结论句，前半句加粗：“**下降约 40% 来自月付涨价。** 月付两类订阅的续费率各降 2.0pt……” | 图上方一行要点句 |
| 图标题 | 读者第一眼能在图上验证的结论：“只有涨了价的月付续费率下降，年付持平” | 同左 |

三条硬规则：

1. **首句要能被反驳。**“本章介绍……”不是结论；“没有变化”“建议先合并”才是。
2. **按同一个问题组织证据。** 互相关联的总览、对比、明细可以放在同一章同一页；出现和本章无关的问题再拆开，不为了“一页一图”机械拆页。
3. **通读测试**：把所有章首句和图标题抄出来连着读，就该是一份完整的汇报。缺一环补一环，多一环删一环。

## 哪些东西不进正文

| 来源 | 例 | 怎么处理 |
|---|---|---|
| 方法铺在结论前面 | 章首写“为了判断效果，我们先定义了……” | 章首给结论，判定方法用一段人话放到章末，公式进口径说明 |
| 交代进度的句子 | “至此第一步完成”“与上一节互相印证” | 删 |
| 预防质疑的辩护 | “之所以不用 X 口径，是因为……” | 删；读者真会问的放进“需要关注” |
| 中间过程的数 | 结论段里出现四五个过渡数字 | 结论只留头条数字，其余留在章节的表里 |

## 人话和公式的分工

判定规则、模型逻辑这类读者不懂就读不下去的内容，按这个顺序写：**先用人话说一遍 → 再给公式 → 再给一个带真实数字的例子**。人话要形象但准确，仍是完整的书面句。系数和阈值都注明性质：数据、用户定的、还是假设。

## 分析类汇报的四条

1. **判断要有对应的证据**：需要量化就给数字和比较基准，并说明业务含义；观察可以是重要事实，但不能冒充原因。算术上的贡献大，不单独证明是原因。
2. **数字带分母和参照**：写“6,300 个，占当周到期的 31.5%”，不单写“6,300 个”；每一层剔除写出剔了多少。
3. **没测出变化时只有四种写法**：采用、拒绝、幅度小到可以忽略（事先定好阈值）、数据不足分辨不出。写“未观察到可识别的变化，幅度在 ±X 以内”，不写“无效果”“无关”。
4. **异常只写证据支持到的原因**：没有过程证据就写“未确认”，并给出要核查的对象；真的开始核查了才写“在查”。

## 指标波动的讲法

解释一个比率为什么升了、为什么比别人高时，按下面的顺序讲，每一步尽量配图，文字只留两三条：

1. **先判断算不算异常**：不只是“高于目标”，突然的较大波动也算。同一份材料用同一个判定标准，并写在页上。
2. **先看走势**：用折线交代最近几期的表现和比较对象，再讲变化。
3. **用瀑布图拆变化**：起点和终点就是标题里那个指标的两个值（例：续费率 80.8% → 77.0%），中间各柱加起来等于变化量；分不到类的部分单列成最后一根柱，写明多大。
4. **比率的变化要把分母算进去**：先看构成（分母里各类的比例）变没变，再看各类自己的比率变没变。只拆分子会把“人变了”误当成“人的行为变了”。
5. **顺着最大的那一块往下拆**：哪类问题最大就展开哪类，不必每类都拆到底。
6. **突出听众能改的部分**：汇报对象能改什么，就把那部分讲细。
7. **全篇一个口径**：放在一起比的两组数，要同一套标签、同一个来源、同一时间范围；口径不同就不并排比。
8. **细节服务主线**：会引出主线以外追问的数和词，不放进页面（例：单独标红一个渠道的高值却不解释）。
9. **先查业务事件**：解释波动之前先查知识库的《业务事件日历》（促销、调价、版本上线、系统切换、节假日）。对得上的只写“同期有××（日期）”，不写成原因；日历里有影响数据的才引用并带出处；查不到写“待业务确认”。新查清的事件补进日历。

图表数字验收员（`chart-number-checker`）验收时也对照这一节。项目自己的口径和用词写在项目根目录的 `_CONVENTIONS.md`。

## 常用章节模板

| 类型 | 骨架 |
|---|---|
| 方案或建议 | 结论与建议 → 现状与问题 → 方案 → 预期效果 → 测算依据 → 风险与配合 |
| 效果评估或复盘 | 结论与建议 → 背景与安排（短）→ 每个问题一章 → 结论的适用范围 → 风险与配合 → 口径说明 |
| 机会分析 | 结论与建议 → 可执行的规模 → 价值对比 → 时效性 → 候选和起步方案 → 资源与风险 → 待决定事项 |
| 归因专题（汇报片） | 总量走势 → 逐层拆解 → 案例佐证 → 影响 → 下一步 |

确有风险、配合或待决定事项时才写对应的结尾章；已有用户认可的结构优先。不写空泛的“需进一步讨论”，不替业务定目标，也不为了套模板新增行动。用户认可过的成品记在 `references/approved-examples.md`，按类型对照着看。

## 交付前自检

按本轮目的取用，不机械套篇幅：

1. 开头让读者知道这次的问题、当前答案或证据边界；讨论稿不硬造定论。
2. **骨架先亮出来**：新写文档或做片时，把骨架（每章或每页一句结论）写在回复开头和进度卡第一步，让用户先判断方向；交给读者验收员 `cold-reader` 时把骨架一起给它，由它核对内容撑不撑得住每句结论。
3. 通读测试通过；同一层的理由同类、有序（按时间、结构或影响大小）。
4. 每张图、每张表都服务本轮的理解、判断或复核；重复的合并，无关的删。
5. 反驳预演：读者最可能问的三个问题，材料里有没有答案；没有的放进“需要关注”。
6. 不确定的结论写成“分辨不出”“不能归因”，不写“无效”“无关”。
7. 用词和图里的字交给 `report-writing` 的 `style_lint.py` 和出图自检。
8. 用户定的事项、假设值、外部输入三者分清并标来源；每个数都能指回一张表或一个口径。

## 会前追问清单

用户说要汇报、汇报前、或者材料要给管理层看时，在交付那条回复的末尾附一份《会前追问清单》：8 到 10 个最可能被问到的问题，每题一句话答案、对应第几页、依据哪个数；现有材料答不了的写“现有材料答不了，需要……”。它只给用户看，不放进正式稿，也不另发文件。

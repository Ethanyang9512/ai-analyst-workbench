# 答案先行的汇报骨架

一份材料读不下去，很少是因为句子不好，多半是因为顺序错了：作者按自己分析的顺序讲（先做了 A、再做了 B），读者却要先知道答案。本技能只管顺序和“每章那一句话”。

**最快的诊断**：只读各章的第一句。读出来的是完整结论，骨架就立住了；读出来的是“我们先看了……然后看了……”，就要重排。

## 动笔前先想清三件事

不必让用户再填一遍，用已经确认的背景在心里答完：

| 问题 | 决定什么 |
|---|---|
| 读者是谁？这次要回答什么、或者要他做什么？ | 解释的深度、证据的顺序 |
| 现有证据能支持到哪一步？ | 首句说多重：哪些是事实、哪些是判断、哪些还待验证 |
| 全篇最该被记住的那一两个数是什么？ | 放在第一章第一屏，其余数字进各章 |

不是每份材料都在请人拍板。讨论稿、盘点、数据还不全的时候，先把已知部分讲清楚，不为了套模板编一个结论。

## 取数之前先写故事线清单

故事线不等分析做完才写。数据还没齐时，先写下“第一天的答案”：当前最好的判断，还是假设也照写。用它决定先查什么、要什么数，再拿数据去证实或推翻。故事线由你起草、用户审，不等用户口述。

- **什么时候写**：开新分析、换新角度、新专题的第一份取数需求、搭新文档或汇报片的结构之前。小改、只答一个口径、例行刷新的数不用写。用户说“先讨论”“先聊清楚再动手”时，只在回复里列草稿，不写文件。
- **写在哪**：项目目录里的 `故事线清单_<主题>.md`，同一主题一份，更新时改原文件。模板和一个完整的例子见 `references/storyline-ledger.md`。
- **写什么**：读者与决策；一句话答案和三分钟版本（三到五句话讲完整件事）；每章一行：章首句｜状态（待验证 / 已证实 / 被推翻）｜证据｜要什么数｜反面证据；改动记录。
- **怎么用**：先验证估计影响最大的候选原因，往哪下钻以算出来的贡献为准。状态只按算出来的结果改；被推翻的那句改写成新发现，原句记进改动记录。交稿时还没验证完的，改成一行“原因待××确认”（××写由谁确认、要查什么；状态留待验证），或移出正文。几份下来一句都没被推翻，回头看反面证据是不是没认真找。
- **给用户看什么**：回复开头亮出读者与决策（一两句）和章首句（带状态，一般不超过 6 条），用户审这一页就够；清单没变就写一句“故事线没变”。目的或读者说不清时先问。

## 决策类材料的默认骨架

```
第一层 答案   一、结论与建议：2–4 条结论（每条一句加粗判断 + 至多一句支撑）+ 一段建议
第二层 理由   二…N、一个问题一章：章首句就是这一章的结论，后面跟证据、原因、限制
第三层 依据   口径说明 / 附录：怎么算的、为什么这么算、数据从哪来
```

- **每章内部也倒过来**：首段给这一章的答案 → 证据（表或图，各配一句要点）→ 原因或限制 → 判定口径放章末。读者看到表之前已经知道结论，表只是验证。
- **开场压成两三句，不单独成章**：先说双方都认的事实，再说什么变了，然后是由此要回答的问题，紧接着给答案。这就是 SCQA（情境、冲突、问题、答案）的压缩版。
- **「需要关注」只收两类**：要别人配合做的事；会改变决策的风险。读者可能会问的其他问题，写进会前追问清单或给用户的回复，不进正文。

## 三种“一句话”的分工

| 位置 | 文档 | 汇报片 |
|---|---|---|
| 章节或页标题 | 中性的名词短语：对象 + 维度（“月付涨价前后的续费率对比”）；项目约定页（用户项目根目录的 `_CONVENTIONS.md`）另有规定时照项目 | 结论句：主语 + 方向 + 数字，可带“模块 \| ”前缀标明属于论证的哪一枝 |
| 章首句 | 结论句，前半句加粗：“**下降约 40% 来自月付涨价。** 月付两类订阅的续费率各降 2.0pt……” | 图上方一行要点句 |
| 图标题 | 读者第一眼能在图上验证的结论：“只有涨了价的月付续费率下降，年付持平” | 同左 |

三条硬规则：

1. **首句要能被反驳。**“本章介绍……”不是结论；“没有变化”“建议先合并”才是。
2. **按同一个问题组织证据。** 互相关联的总览、对比、明细可以放在同一章同一页；出现和本章无关的问题再拆开，不为了“一页一图”机械拆页。
3. **通读测试**：把所有章首句和图标题抄出来连着读，就该是一份完整的汇报。缺一环补一环，多一环删一环。

## 哪些东西不进正文

| 来源 | 例 | 怎么处理 |
|---|---|---|
| 方法铺在结论前面 | 章首写“为了判断效果，我们先定义了……” | 章首给结论，判定方法用一段人话放到章末，公式进口径说明 |
| 交代进度的句子 | “至此第一步完成”“与上一节互相印证” | 删 |
| 预防质疑的辩护 | “之所以不用 X 口径，是因为……” | 删；会改变决策的风险才放进“需要关注”，读者可能问的其他问题写进会前追问清单 |
| 中间过程的数 | 结论段里出现四五个过渡数字 | 结论只留头条数字，其余留在章节的表里 |
| 跑题的旁枝 | 讲续费率时顺带提了新购转化率 | 不进正式稿：记进故事线清单的“不在本次范围”，在回复里一句话点出，要不要另做由用户定；本文答不了、又不影响决策的问题不提 |

## 人话和公式的分工

判定规则、模型逻辑这类读者不懂就读不下去的内容，按这个顺序写：**先用人话说一遍 → 再给公式 → 再给一个带真实数字的例子**。人话要形象但准确，仍是完整的书面句。系数和阈值都注明性质：数据、用户定的、还是假设。

另外三个让读者少费劲的做法（这是做法，不是固定格式；怎么放按内容定）：

- **分析里新定义的口径第一次出现时，配一张“定义卡”**（这是要业务去盯的新口径，名字用业务听得懂的话，不是自造术语）：在那一处并排放三样：识别标准（写到能直接做成看板指标的程度，含“正常”怎么定）→ 有多少（占比，带对标）→ 有多严重（平均差多少）。例（数字为虚构）：“到期前 7 天内取消了自动续费的订阅”，占当周到期的 9.4%，比 W1–W5 平均高 2.1pt。后面要盯的指标就用这个定义。
- **加法或乘法拆解可以画成“算式图”**：每一项一张小图，图之间用大号的“＋”“×”连起来，圈出差距最大的那一项，每张小图下面一句判断（略降 / 影响小 / 降得最多），代替一行文字公式。
- **统计结论后面紧跟一两个真实案例**：挑能看出“问题是怎么发生的”的真实记录（时间线、前后对照），案例下面放三个小数字：实际、正常、条件。例：“到期前 3 天取消 ／ 平时续费 ／ 涨价通知发出后第 2 天”。

## 分析类汇报的六条

1. **判断要有对应的证据**：需要量化就给数字和比较基准，并说明业务含义；观察可以是重要事实，但不能冒充原因。算术上的贡献大，不单独证明是原因。
2. **数字带分母和参照**：写“6,300 个，占当周到期的 31.5%”，不单写“6,300 个”；每一层剔除写出剔了多少。关键数同时给绝对值和相对值，再配一个最能说明好坏的对标（项目约定页或用户指定的优先）；找不到合适的对标，正文不写“无对标”，在给用户的回复里说一句。
3. **没测出变化时只有四种写法**：采用、拒绝、幅度小到可以忽略（事先定好阈值）、数据不足分辨不出。写“未观察到可识别的变化，幅度在 ±X 以内”，不写“无效果”“无关”。
4. **异常只写证据支持到的原因**：没有过程证据就写一行“原因待××确认”（××写由谁确认、要查什么）；真的开始核查了才写“在查”。拆解只回答“变化落在哪”，不回答“为什么”；只是同期发生的，写“同期有××（日期）”。
5. **先判有没有问题**：没超出正常波动的指标一句带过；没有新发现就直说“没有明显变化”。完整底稿和用户要的正常对照照留。
6. **原因判断分强弱，全篇一个标准**：查过的每个可能原因都给出判断，并分清强弱：主要原因、放大因素（让问题变严重但不是根源）、影响小、数据不支持、只是时间对得上。判断的说法以项目里已经定下的为准，不套固定用语；同一份材料里同一种强弱只用一个说法，并在用到的地方写清判断标准（例：“影响小＝解释不了大部分差距”）。“约占一半”这类份额写明怎么算的。定为主要原因，除了拆解算出的份额，还要有过程证据（真实案例、对照组）；只有份额时，只说差距主要落在哪（同第 4 条）。

## 指标波动的讲法

解释一个比率为什么升了、为什么比别人高时，按下面的顺序讲，每一步尽量配图，文字只留两三条：

1. **先判断算不算异常**：不只是“高于目标”，突然的较大波动也算。同一份材料用同一个判定标准，并写在页上。动手拆之前先验指标本身：口径或采集方式改没改、取数任务断没断、最后一天的数据到齐没有、日历和季节因素。
2. **先看走势**：用折线交代最近几期的表现和比较对象，再讲变化。
3. **用瀑布图拆变化**：起点和终点就是标题里那个指标的两个值（例：续费率 80.8% → 77.0%），中间各柱加起来等于变化量；分不到类的部分单列成最后一根柱，写明多大。出图前对账，对不上不出图：首柱、末柱等于两期的值，中间各柱加起来等于差额，中间柱和首尾同一单位（逐条检查见 `references/metric-bridges.md`）。
4. **比率的变化要把分母算进去**：先看构成（分母里各类的比例）变没变，再看各类自己的比率变没变。只拆分子会把“人变了”误当成“人的行为变了”。构成变化为主时，问题不在哪一类里面，往下钻会钻偏。两种拆法的公式、算例和注意点见 `references/metric-bridges.md`。
5. **顺着最大的那一块往下拆**：哪类问题最大就展开哪类，不必每类都拆到底。每下钻一层，先算各候选维度（方案、渠道、地区、日期等）对总变化的贡献，沿最集中的那一支走；贡献很小的不展开，底稿留着。试过哪些维度、为什么选这一支，记在故事线清单或底稿里，不写进正文。
6. **突出听众能改的部分**：汇报对象能改什么，就把那部分讲细。
7. **全篇一个口径**：放在一起比的两组数，要同一套标签、同一个来源、同一时间范围；口径不同就不并排比。两边结构不同（方案构成、渠道、新老用户比例）时，先按同一结构调平再比（把两边换成同样的构成再算），并在图头写出调平了什么（“同方案构成比”）；全篇的比较期固定，每张图用同一种底色标出比较期。
8. **细节服务主线**：会引出主线以外追问的数和词，不放进页面（例：单独标红一个渠道的高值却不解释）。
9. **先查业务事件**：解释波动之前先查知识库的《业务事件日历》（促销、调价、版本上线、系统切换、节假日）。对得上的只写“同期有××（日期）”，不写成原因；日历里有影响数据的才引用并带出处；查不到就写一行“原因待××确认”。新查清的事件补进日历。
10. **拆解顺序讲得出理由**：几个因素相乘（如用户数 × 付费率 × 客单价）时，先算谁会改变各自分到的份额。要么说明为什么按这个顺序，要么用各种顺序取平均的拆法；项目已经在用的拆法沿用，要换先跟用户说。分不到类的部分占多少就继续拆、下钻在哪停、正常波动带多宽这几个数，用户定之前按 `references/metric-bridges.md` 的参考值做，并在回复里说一句用了参考值。
11. **用天然对照组排除外部因素**：要说“不是季节、大盘、节假日”之前，找一个受同样外部条件影响、但没出这个问题的对象（另一个方案、另一个渠道、另一个地区）。它没变，就能排除外部因素。例：同一周到期、没涨价的年付，分首次 / 多次续费看，两类的续费率都没变，所以月付续费率下降不是季节或大盘造成的。对照组也要按同一结构比：年付合计的续费率掉了，那是首次续费的变多了（构成变化），不是年付的人续得少了。找不到对照组时，不写“排除”。

图表数字验收员（`chart-number-checker`）验收时也对照这一节。项目自己的口径和用词写在项目根目录的 `_CONVENTIONS.md`。

## 常用章节模板

| 类型 | 骨架 |
|---|---|
| 方案或建议 | 结论与建议 → 现状与问题 → 方案 → 预期效果 → 测算依据 → 风险与配合 |
| 效果评估或复盘 | 结论与建议 → 背景与安排（短）→ 每个问题一章 → 结论的适用范围 → 风险与配合 → 口径说明 |
| 机会分析 | 结论与建议 → 可执行的规模 → 价值对比 → 时效性 → 候选和起步方案 → 资源与风险 → 待决定事项 |
| 归因专题（汇报片） | 总量走势 → 逐层拆解 → 案例佐证 → 影响 → 下一步 |
| 诊断专题（为什么变差、要给建议；文档和汇报片通用） | 结论与建议（含“问题、原因、建议”总表）→ 界定问题 → 按问题树逐层缩小范围 → 每个问题一章，章末配它的建议 → 附录一：查过的原因及判断 → 附录二：逐条证据。思路见下一节 |

确有风险、配合或待决定事项时才写对应的结尾章；已有用户认可的结构优先。不写空泛的“需进一步讨论”，不替业务定目标，也不为了套模板新增行动。用户认可过的成品记在 `references/approved-examples.md`，按类型对照着看。

## 诊断专题的骨架

“为什么变差了”“为什么比别人差”、最后要给建议的专题，文档和汇报片都按这条推理链组织。这是推理结构，不是固定格式；标题、表头、判断用语按本项目的内容和已定写法来。

- **先界定问题**：拆原因之前，先确认问题真实存在、有多大、和谁比、还在不在恶化（同比、对标组、外部基准、最近走势）。读者先认同“这是个问题”，后面才听得进原因。
- **问题树，逐层缩小范围**：按业务过程把可能的原因拆成一棵不重不漏的树（例：到期的人变了、价格变了、产品体验变了、扣款渠道出问题、外部环境）。每一步用数据确认问题落在哪一支，同时交代其余分支为什么可以先放下；下一步只在留下的范围里继续拆，范围沿用上一步的定义。拆到能对上具体动作和负责的对象（某个环节、某类用户、某个渠道）为止。
- **因果链分清强弱**：现象 → 落在哪 → 怎么发生的（靠真实案例、对照组这类过程证据）→ 什么让它变严重 → 建议。主要原因、放大因素、影响小的、数据不支持的、只是时间对得上的，分开说，不混成“原因之一”（见“分析类汇报的六条”第 6 条）。
- **建议和原因一一对上**：每条建议都能追到一个已证实的原因，每个原因都能追到证据。问题和它的建议放在一起讲，读者始终知道这一部分在回答哪个问题。用一张总表把“问题、原因、建议”连起来并标出处（问题有两个以上时，三列表好用）；文档放在第一章「结论与建议」，汇报片现场讲时可以放在主线末尾。
- **把排除过程也交给读者**：查过的原因（含排除掉的）汇成一张总表放附录一，每条写数据、判断和出处，内容直接从故事线清单来。读者最常问“是不是因为××”，这张表让他自己找到答案。

**建议怎么写**：确需行动时，每条建议回答四件事：做什么；谁已经在做（写清来源）；盯哪个指标（现值、对标、多久看一次、按什么粒度）；能改善多少、要付出什么（用测算回答，例（数字为虚构）：“给多次续费的月付用户发续费折扣，月付多次续费率 82% → 84%，每月多付约 9 万元折扣（每单约 2 元）”，并写出最近一期还剩多少空间）。只写“做什么”，读者没法拍板。按问题类型把对象分组，每组对一个动作。第一章「结论与建议」里每条建议只写一句（谁、做什么、什么时候），四件事展开写在对应问题章的末尾。

## 交付前自检

按本轮目的取用，不机械套篇幅：

1. 开头让读者知道这次的问题、当前答案或证据边界；讨论稿不硬造定论。
2. **骨架先亮出来**：新写文档或做片时，把骨架（每章或每页一句结论，也就是故事线清单的章首句；交稿时，写成结论的章首句都要是“已证实”，没验证完的只能以一行“原因待××确认”出现，或移出正文）写在回复开头和进度卡第一步，让用户先判断方向；交给读者验收员 `cold-reader` 时把骨架和状态一起给它，由它核对内容撑不撑得住每句结论。
3. 通读测试通过；同一层的理由同类、有序（按时间、结构或影响大小）。
4. 每张图、每张表都服务本轮的理解、判断或复核；重复的合并，无关的删。
5. 反驳预演：读者最可能问的三个问题，材料里有没有答案；会改变决策的风险放进“需要关注”，其余写进会前追问清单或给用户的回复。
6. 限定、待确认、备选数过一遍：删掉它读者也不会做出不同决定的，就删；“请业务确认我们的理解”改写成“按 X 测算；若为 Y，结果变为 Z”。
7. 不确定的结论写成“分辨不出”“不能归因”，不写“无效”“无关”。
8. 用词和图里的字交给 `ethan-report-writing` 的 `style_lint.py` 和出图自检。
9. 用户定的事项、假设值、外部输入三者分清并标来源；每个数都能指回一张表或一个口径。

## 会前追问清单

用户说要汇报、汇报前、或者材料要给管理层看时，在交付那条回复的末尾附一份《会前追问清单》：8 到 10 个最可能被问到的问题，每题一句话答案、对应第几页、依据哪个数；现有材料答不了的写“现有材料答不了，需要……”。它只给用户看，不放进正式稿，也不另发文件。

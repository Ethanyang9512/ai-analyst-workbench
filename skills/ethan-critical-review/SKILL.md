# 第一性原理加对抗式审查

“检查一遍”和“试着驳倒它”是两件事。前者容易看什么都顺眼；后者要求换到反对者的位置上，**找不到能驳倒它的地方才算过**。

两层缺一不可：

- **第一性原理**：把交付物拆回最底层的事实和假设，逐条问“这是数据支持的，还是想当然的？来源是什么？”。“上一版就是这样”“业内都这么做”不算来源。
- **对抗**：从几个互相独立的视角分别进攻，每个视角都假设作者错了，去找证据。

## 怎么做

1. **列假设清单**：交付物依赖的全部假设、口径和参数，每条标来源（数据 / 用户拍板 / 作者假设）。“作者假设”的那几条必须明着给用户看。
2. **选 3–5 个视角分别进攻**，按对象挑：
   - 逻辑：内部有没有自相矛盾；公式和文字描述是否一致；
   - 口径：字段含义、时间对齐（节假日错位、业务日期和日历日期、时区）、单位、去重；
   - 边界：极端值、零值、某个分组整个缺失时会怎样；
   - 业务合理性：反直觉的结果能不能解释；人能感知的量级（单价、人均、日均）对不对；
   - 使用者：业务同事拿到手能看懂、能操作吗。
   复杂对象可以让几个子代理并行，各攻一个视角，避免自己审自己。
3. **写发现清单**：每条标 P1（错误，必须修）/ P2（缺陷，应该修）/ P3（建议，用户定），并写清“在什么输入下会得出什么错误结果”。
4. **修一条验一条**：P1、P2 修完逐条复核，不能修完就宣布通过。
5. **汇报**：攻了哪些视角、发现了什么、修了什么、哪些 P3 留给用户定。**零发现也要说清攻了哪里、为什么没攻破**，“没问题”三个字不算审查报告。

## 两个边界

- **审查不是扩大范围的理由。** 只审用户要的那份交付物；发现范围外的问题，列出来让用户定，不顺手改。
- **别往稿子里加防杠句。** 审查发现“读者可能误解”时，正确的处理是把那句话本身改准，而不是再加一句预先反驳的澄清。读者真会问的，放进“需要关注”。

## 让用户看得到进度

审查常常耗时，而用户看不到你在跑什么。开始时说分几步、大概多大；每完成一个视角说一句；不要长时间没有动静。

## 一个小例子（虚构）

对象：一份“续费率下降归因”的报告。

| 视角 | 攻击 | 结论 |
|---|---|---|
| 口径 | 分母用的是到期订阅数还是活跃订阅数？两周的分母口径一致吗？ | 一致，过 |
| 口径 | 扣款时间是 UTC，汇总前换成本地时间了吗？ | 没换：W6 周日的续费有 140 个落到了 W7。P1，重算 |
| 逻辑 | “构成变化 −2.3pt + 续费率变化 −1.5pt”加起来等于总变化吗？ | 等于 −3.8pt，过 |
| 业务合理性 | 年付首次续费 58% 的续费率合理吗？和去年同期比呢？ | 和去年同类订阅接近，过；补一句出处 |
| 使用者 | “构成变化”业务看得懂吗？ | 看不懂。P2：第一次出现时补一句解释和一个例子 |

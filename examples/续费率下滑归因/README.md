本例数字均为虚构：“示例 App”是一款编出来的订阅制修图工具，方案、价格、事件和全部数字都是编的，只用来演示工作台怎么用。

# 示例项目：续费率下滑归因

示例 App 的周续费率从 W6 起掉了约 4pt，增长负责人想知道为什么。这个目录是这个项目在分析助手工作区里的样子。下面按时间顺序走一遍九步：提需求 → 开题 → 给取数助手的需求 → 审数据包 → 先亮骨架再写 → 交付前验收 → 用户手改定稿 → 存成对稿 → 收尾回流知识库。每一步都标了用到的技能、程序和文件。

## 先跑一下：报告里的数从哪来

```bash
cd examples/续费率下滑归因
python3 analysis/recompute.py
```

它只读 `data/weekly_by_segment.csv`（取数助手交来的明细按周、方案、首次/多次续费汇总后的结果），打印报告用到的每一个数：周走势、两类未续费、构成变化和续费率变化各拉低多少。报告、骨架、指标卡里的数都能在这份输出里找到。这就是第一条设计原则“数字只能由代码算出来”在一个项目里的样子。

## 这个例子演示什么

- **拆解一个比率的变化**：续费率掉了，先分“到期的人变了”（构成变化）和“同一类人续得少了”（续费率变化），两项相加正好等于总变化。
- **同期发生不等于原因**：月付涨价和首年优惠到期发生在同一周，用没涨价的年付当对照，才能把涨价的影响说实。
- **整套约定怎么落地**：五要素 brief、取数字段清单、自足的需求包、审核报告、约定页、术语表、现状摘要、成对稿、知识库回流。

想看另一种题型（实验评估、结论是“分辨不出”），见 [../新手引导改版评估/](../新手引导改版评估/)。

## 第 1 步：用户在群里提需求

> 用户：续费率 W6 开始掉了 4 个点左右，帮我查一下原因，下周一周会要讲。

桥把消息转给分析助手时，每轮提醒钩子（`runtime/hooks/remind.py`）在消息后面补上长期要求：先一句话写出理解、只做被要求的、用大白话；消息里有“周会要讲”，再提醒交付时按全稿验收、回复末尾附会前追问清单。分析助手先回一句理解：

> 我的理解：查续费率 W6 起下降的原因，分清是主动取消还是扣款失败、集中在哪类订阅，周会前给一份报告；不分析新购，不做 PPT。先开题，有一个问题要确认：分母用当周到期的订阅数可以吗？

## 第 2 步：开题（`analysis-brief`）

分析助手按五要素写 [brief.md](brief.md)：背景、要回答的问题、交付形式、限制、检查点。动手之前，先叫一个子代理**只攻分析设计**（不碰数据），攻出四条。最要紧的两条：

- 分母要用当周到期订阅数，用活跃订阅数会被稀释；
- W6 到期的人和 W5 不是同一批：去年首年优惠买的年付订阅从 W6 起第一次到期，所以字段清单里必须要“方案”和“首次/多次续费”。

用户确认分母后，这一条当轮写进 [_CONVENTIONS.md](_CONVENTIONS.md) 第 3 条。口径类的决定第一次就写；用词类的纠正，第二次出现才写。

## 第 3 步：给取数助手的需求（`data-package-review`）

取数助手负责写 SQL、跑数、交数据包，可以是同一台电脑上另一个智能体会话，也可以是同事。新专题的第一份需求写成 [取数字段清单.md](取数字段清单.md)，**一次要齐后面可能要切的维度**：方案、首次/多次续费、渠道都要了，渠道是预留的，之后换角度在本机算。清单里还专门写了一条“时间字段统一成本地时间”，因为扣款流水默认是 UTC。

[需求包_v1.md](需求包_v1.md) 是自足的：背景、最新决定、要做的、保留不动的、验收条件、附清单原文。分析助手这一轮回复的最后一行固定是：

> 给取数助手：需求包_v1_20260310.md。还需要取数助手做的事：有（已写在包里）。

取数助手按 `reproducible-analysis` 交 SQL：一步一个文件、带 header 注释（口径和过滤原因写在注释里）、变更记进 [sql/_CHANGELOG.md](sql/_CHANGELOG.md)。

## 第 4 步：审数据包

数据包（zip）回来，分析助手先用 `extract_package.py` 解到 `round1/pkg/`（新目录、不覆盖、拒绝越界路径），再跑 `pkgcheck.py`（说改了没重跑、公式缓存为空、明文个人信息、时间窗缺天），然后按六个攻击点人工审，并做一次最小的独立复算。结果写成 [round1/审核报告_v1_示例.md](round1/审核报告_v1_示例.md)：

- 一条 P2：核对文件按 UTC 日期切周，和按本地时间的明细对不上；
- 一条 P3：渠道名称有两种写法。

两条都在本机处理，**不拉取数助手全量重做**。没有实质问题，审核就结束，不固定轮次。

## 第 5 步：先亮骨架，再写正文（`pyramid-storyline` → `report-writing`）

分析助手先给用户看 [报告骨架.md](报告骨架.md)：每章只有一句结论和图标题。**通读测试**：只读每章那一句，就能把事情讲完。

骨架里最关键的一句来自 `analysis/recompute.py` 的拆解：W5 到 W6 下降 3.8pt，其中构成变化拉低 2.3pt（首次续费占比从 21.1% 升到 29.0%），各类续费率变化拉低 1.5pt（全部来自月付；年付没涨价，续费率没变）。用户确认后，分析助手按 `report-writing` 写正文、按图表规范出图，得到报告第一版（[交付版](../../exam/example-paper/delivered.md)）。

## 第 6 步：交付前验收

1. **程序检查**（几秒钟，真实输出见 [outputs/](outputs/)）：`style_lint.py` 查硬禁词、`deckcheck.py text` 查约定页里的禁用词和同一个东西几种写法、`figcheck.py` 查图里文字重叠和出界、`trace_scan.py` 查内部痕迹（协作方名字、过程用词、本机路径）。
2. **定档**：新写的第一版、用户又说“周会要讲”，按**全稿**验收。
3. **两位验收员**（子代理）：读者验收员只读成品和术语表，像一个没有背景的业务同事那样冷读，提出“首次续费”首次出现没解释；图表数字验收员逐张看图、回 `data/` 抽核 12 个数、对照约定页，无必须改。只有必须改才返工。
4. **写验收记录**，再另起一条命令发送：

```bash
python3 "$AAW_RUNTIME/tools/accept_record.py" write --file 报告_v1.pdf --tier full --pages "全稿" \
        --reader "冷读通过，补了“首次续费”的首次解释" --visual "4 张图看过，核了 12 个数，无必须改"
lark-cli im +messages-send --as bot --chat-id <本轮 chatId> --file 报告_v1.pdf
```

发送前，验收门（`runtime/hooks/gate.py`）按文件内容指纹查这条记录；护栏（`runtime/hooks/guard.py`）确认带了 `--as bot`、发的是本群。回复里写一行验收结果，末尾附会前追问清单（用户在周会上可能被问到的 8–10 个问题）。

## 第 7 步：用户手改定稿

用户在飞书文档里直接改，改完的样子是[用户定稿](../../exam/example-paper/final.md)。分析助手回读线上稿、和交付版比对，把手改同步进生成源（不然下次重建会冲掉），得到 `报告_v2.md`。用户改了这些：

- 删掉“分析过程”那段，第一部分只留结论；长长的加粗句拆成一句短的加粗结论加一段解释；
- 删“值得注意的是”、删内部包号和“仅供参考”、把“断崖式下跌”改成“下降”、“我们认为”改成“数据显示”、百分比保留一位小数、“续订”统一成“续费”；
- 删掉没有数据支撑的“其中多为对价格敏感的学生用户”；
- 对过源数据，把年付首次续费 W6 的续费率从 57.0% 改成 58.0%（事实改动）。

## 第 8 步：存成对快照，纠正当轮沉淀

```bash
python3 ~/.claude/skills/report-writing/scripts/pairsnap.py save --project renewal-analysis --doc 续费率报告 \
        --delivered 报告_v1.md --final 报告_v2.md
```

`pairsnap.py` 存下交付版、定稿和差异，算出手改比例 0.33（交付版正文 30 行里改了 10 行）、篇幅比 0.89。每 3 份新成对稿留 1 份当考题；这份是第 2 份，不是考题，所以可以从里面提取改法。

“值得注意的是”“仅供参考”都是用户**第二次**删，按“修正即沉淀”写进 [_CONVENTIONS.md](_CONVENTIONS.md) 第 6、7 条，并进 json 检查块的 `banned`，下次 `deckcheck.py` 会直接报出来。只出现一次的改法（比如“保持在”改成“仍是”）先记在项目状态里，不升成规矩。

## 第 9 步：收尾，回流知识库

项目结束，分析助手按 `templates/knowledge-base/项目收尾清单.md` 整理八项给用户看，用户同意后回流三处（见 [知识库片段/](知识库片段/业务事件日历_片段.md)）：

- 指标卡《续费率》（[知识库片段/指标卡_续费率.md](知识库片段/指标卡_续费率.md)），把“时区”“太早取数”“构成变化”三个坑写进去；
- 业务事件日历补三行：涨价通知、月付涨价、首年优惠到期潮，只写“同期发生”和有数据的影响；
- 项目索引补一行。

[_status.md](_status.md) 的现状摘要更新成“项目已结束”。

## 这一对稿后来成了示例考卷

“交付版 → 用户定稿”这一对，正是 [exam/example-paper/](../../exam/example-paper/) 里的考卷：拿交付版让分析助手按规则自查一遍，用代码比它的改法和用户的改法有多接近。怎么出卷、怎么考、怎么打分，见 [exam/README.md](../../exam/README.md)。
